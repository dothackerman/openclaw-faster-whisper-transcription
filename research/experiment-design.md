# Local dictation experiment protocol

Status: research protocol, 2026-09-29. No benchmark results yet. This document does not authorize installing a plugin, changing OpenClaw configuration, recording anyone, or running GPU tests on the live Gateway host.

## Objective and boundary

Optimize **the actual browser dictation path** for intelligible German/English text that the user can inspect and edit before sending, while minimizing time to useful preview, time to final text, and incremental GPU load. A fast offline file-transcription benchmark is necessary but insufficient: browser capture, audio transport, chunking, provider session lifecycle, and composer insertion must be included in the final evaluation. The active OpenClaw 2026.9.6 checkout contains browser-dictation UI strings and tests for partial/final transcript behavior (`ui/src/pages/chat/composer-dictation.test.ts`, `ui/src/e2e/browser-dictation-status.e2e.test.ts`); the exact plugin-side contract must be locked from that release before implementing the harness. [OpenClaw provider voice capability guide](https://docs.openclaw.ai/plugins/sdk-provider-plugins/voice-and-audio).

The local machine currently reports an **NVIDIA GeForce RTX 3060 Laptop GPU, 6,144 MiB, compute capability 8.6**, driver 580.178.04. At the read-only inspection time, 551 MiB was already allocated and GPU utilization was 36%; therefore raw VRAM/power readings cannot be attributed wholly to this plugin. The goal is incremental load against a paired idle baseline, not a misleading absolute number. Verify the operating state afresh for each run.

## Autoresearch adaptation

Borrow the small, repeatable loop from [Karpathy's autoresearch program](https://github.com/karpathy/autoresearch/blob/master/program.md): immutable preparation/evaluation, one hypothesis per experiment, a fixed scorecard, a logged keep/discard/crash decision, and reviewable code/config diffs. Do **not** copy its five-minute training budget or indefinite run mandate: short-dictation inference has a different objective and this shared laptop/Gateway requires bounded experiments. Pin the evaluation corpus and harness; only candidate settings or plugin code may change inside an experiment. Do not tune against the held-out final set.

## Fixture design

Keep two physically separate fixture pools:

1. **Public reproducibility fixtures** in the repository: self-authored scripts and, only if explicitly cleared for publication, short audio recorded by consenting speakers or openly licensed recordings with attribution and redistribution rights. No real chat, meetings, client names, addresses, credentials, or background speech. Synthetic/TTS audio may verify protocol determinism, but it cannot stand in for microphone quality testing.
2. **Private mic-varied corpus** outside the Git worktree, ignored by the repo and never uploaded to GitHub or CI: the user's own recordings made with each actual mic. If other voices are audible, obtain permission for local testing or discard the clip. Record an exact reference transcript locally, but use invented non-identifying names and content in scripts. Do not persist raw transcript or audio in public logs. Store only fixture IDs, hashes, duration, mic class, language, acoustic category, and aggregate scores in public experiment reports. Salted/opaque IDs avoid revealing private filenames.

For each mic, record the **same script** at normal distance and a realistic alternate distance, with ambient conditions noted; also capture a short true silence/no-speech clip. Preserve the untouched browser-captured bytes as the fixture source and derive normalized PCM fixtures deterministically with a pinned FFmpeg version and command. Do not use one mic recording plus digital noise as a substitute for another mic; optional digitally degraded variants are a distinct stress subset. Store SHA-256 for originals and derived audio, sample rate, channels, codec, duration, capture/browser version, mic model or privacy-safe class, placement, and input gain/processing flags (echo cancellation, noise suppression, automatic gain control). Keep an internal manifest to re-run exactly the same set.

Minimum useful matrix before selecting a winner: German and English, short (about 3–5 s) and medium (about 10–20 s) utterances, ordinary prose and punctuation, web-development vocabulary, invented proper nouns/numbers, code-switching, phrase-final pauses, room noise, and silence. Aim for at least 5 independent utterances per important stratum per mic; repeated recordings of one sentence are not independent examples. Reserve a small untouched holdout of scripts/recordings for final confirmation. Never add failures from a candidate to the fixed comparison set mid-series; start a new corpus version if coverage must expand.

## Metric contract

Use a pinned scorer (for example [JiWER](https://github.com/jitsi/jiwer/blob/master/docs/usage.md)) and publish its version and normalization rules. Compare exact final transcript with the reference using **micro-averaged WER** (`substitutions + deletions + insertions` divided by reference words) and **CER**. Normalize Unicode to NFC, case-fold, trim/collapse whitespace, and remove punctuation for the primary lexical score. Retain a separate raw-output score/review for punctuation, casing, numerals, and diacritics; do not hide German umlaut, `ß`, English technical terms, or number errors under aggressive normalization. Predefine tokenization for hyphenation, contractions, and code-switching, and keep it frozen. For silence, report false-positive words separately instead of folding an empty reference into WER; JiWER explicitly supports empty-reference checks. Report pooled and per-mic/per-language/acoustic-stratum WER/CER, plus worst-stratum values, not just a single aggregate. [JiWER usage](https://github.com/jitsi/jiwer/blob/master/docs/usage.md); [JiWER empty-reference behavior](https://github.com/jitsi/jiwer/blob/master/README.md).

Human review is a blinded side-by-side comparison of final transcripts from baseline and candidate for each clip, with order randomized. Record: better/same/worse, meaning-changing errors, technical-term accuracy, missing words, invented words on silence, punctuation usefulness, and whether the text is acceptable to edit/send. Reviewer must listen to the original audio, not infer reference from model output. Count disagreements and adjudicate critical meaning changes explicitly. Automated WER/CER does not capture all edit burden.

Instrument latency with a monotonic clock and the same boundaries for every candidate:

- **Cold start:** provider process/model absent; time from dictation start request to ready, first useful partial, and final composer text. Include model load; exclude first-time model download (pre-provisioned and checksummed).
- **Warm dictation:** loaded resident model, stable system; time from first audio frame to first non-empty partial, and from user Stop/last frame to final text visible in editable composer. Report p50 and p95 over **at least 20 repetitions** of the fixed short/medium subset and per-length values, plus failures/timeouts. A percentile over only a handful of clips is not credible.
- **Quality timing:** partial update cadence and partial instability (number of changed/retracted words) so a fast but unreadable preview cannot win. Record real-time factor `inference_wall_time/audio_duration` separately from user-perceived latency.

Log timings at browser, Gateway ingress/egress, provider receive, model inference start/end, and composer update where feasible. Use trace IDs and monotonic timestamps, no audio/text payloads in ordinary logs. Browser and provider clocks should not be subtracted across machines unless synchronized; use each process's local intervals and a browser-observed end-to-end interval.

For GPU impact, take a 30–60 s idle baseline under similar background workload; poll NVML or `nvidia-smi` at a documented interval (e.g. 200 ms) throughout loading, recording, finalization, and 30–60 s post-run. Record peak and steady **GPU memory used**, utilization, power draw where the driver exposes it, idle-adjusted GPU-memory residency while the model is warm, and peak *incremental* memory versus baseline. Approximate energy as integral of `(power - matched idle power) × time` only if sampling is available/reliable; label it an estimate, not a calibrated meter. In parallel capture process RSS/CPU and whether GPU allocation remains after idle timeout. Repeat across randomized candidate order, on AC power with stable power/thermal state; note temperature/clocks/throttling and any competing GPU process. The local `nvidia-smi` power limit is unavailable, so do not assume it. [NVIDIA System Management Interface guide](https://docs.nvidia.com/deploy/nvidia-smi/index.html).

## Search space, staged in order

Keep a **baseline** of the originally planned `medium` model with automatic German/English language detection, then vary one factor at a time. Use the exact same browser audio and transcript scorer across candidates.

1. **Correctness and transport:** PCM format/resampling, chunk sizes, end-of-stream flush, no dropped/duplicated samples, no stale partial/final insertion. Do not tune inference to compensate for a broken transport.
2. **Big levers:** model size/family (`small`, `medium`, possibly multilingual newer options if compatible and licensed), GPU `compute_type` (`float16`, `int8_float16`, perhaps `int8` if supported), model residency/idle unload, and beam size (1 vs default 5). Check supported compute types on this device at runtime; CTranslate2 may implicitly convert unsupported types. [Faster-Whisper README](https://github.com/SYSTRAN/faster-whisper); [CTranslate2 quantization](https://opennmt.net/CTranslate2/quantization.html).
3. **Dictation-specific quality:** auto-detect vs user-selected German/English, detection window and language carry-over, VAD enable/threshold/minimum silence/padding, segment/chunk length and overlap, partial decoding cadence, initial prompt glossary for technical vocabulary, `condition_on_previous_text`, temperature fallback/no-speech thresholds. Record exact defaults because Faster-Whisper's batched and unbatched VAD defaults differ; silence trimming can remove quiet speech. [Faster-Whisper transcription API](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py); [VAD source](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/vad.py).
4. **Load:** concurrency and batching only after single-dictation latency is good. Throughput benchmarks for 13-minute recordings are not directly predictive of this short, interactive use case; batching may raise VRAM and defer first text. [Faster-Whisper benchmark](https://github.com/SYSTRAN/faster-whisper#benchmark); [CTranslate2 performance tips](https://opennmt.net/CTranslate2/performance.html).

Do a small screening set to eliminate crashes/OOM and obviously inferior settings, then full fixed development-set evaluation for contenders, then a one-time untouched holdout and real browser/mic acceptance test. Do not claim a winner from a single clip, a single timing run, or a published benchmark from another GPU.

## Decision rule and experiment ledger

Before tuning, establish baseline variability with 3 repeated baseline runs. A candidate is **keep** only if it passes transport/correctness tests, has no new meaning-changing critical errors or silence hallucinations on the development set, and is Pareto-improving in at least one target dimension (lower WER/CER or materially lower p95 response time or incremental GPU residency) without a material regression in another. As a practical provisional guardrail, flag >1 absolute percentage point pooled WER increase or >2 points in any important stratum, >10% p95 warm-final increase, or >10% extra warm GPU memory; review against baseline run-to-run variation before deciding. These are screening thresholds, not claims of achieved quality. Prefer the lightest candidate within the observed quality/timing noise band. Record **discard** for dominated runs, **crash** for failed runs, and **inconclusive** when measurement noise or thermal/background interference prevents a comparison. Human-review veto beats a small numerical WER gain.

Maintain `research/experiments.tsv` (or JSONL plus a readable summary) with one row per run: UTC timestamp, experiment ID, hypothesis, code commit, dirty-state check, corpus/manifest hash, scorer and harness hashes, OpenClaw release SHA, Python/Faster-Whisper/CTranslate2/CUDA/cuDNN/driver versions, model ID/revision/checksum, GPU identity, all settings, cold/warm state, fixture subset, run order/seed, WER/CER per stratum, false positives, p50/p95 partial/final latency, peak/incremental/warm GPU memory, power estimate availability, reviewer result, status, and reason. Store sanitized detailed run artifacts outside Git by default; publish only audited aggregate data. Link retained results to code diffs; never rewrite a losing result out of the ledger. The measured candidate must be re-run after any implementation refactor.

## Acceptance and limits

The chosen candidate must pass plugin unit/integration checks, the exact OpenClaw release's provider contract, then a real browser dictation session with **each mic**: visible partial transcript while speaking, final transcript in the editable composer after Stop, no automatic send to the agent, correct cancellation/stale-result handling, and graceful GPU/model failure. Browser-observed p50/p95 and human editability are the decisive outcome. A pure offline result can only nominate a candidate. Do not touch live Gateway configuration or restart it as part of this research protocol.
